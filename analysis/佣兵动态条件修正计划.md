# 佣兵团「动态条件」修正计划

> 状态：**待批准**（未改动任何游戏文件）
> 审计日期：2026-11-23
> 范围：`common/mercenary_companies/` 全部 3 个文件、254 个佣兵团

---

## 0. 一句话结论

254 个佣兵团里有 **236 个**的 `trigger` 里写着会在游戏过程中**反复翻转**的状态条件
（`army_size_percentage` / `ai`），其中 222 个用的是同一套「AI 软门」模板。
原版 1.37.5 的 74 个佣兵团里，这三个词的出现次数是 **0 / 0 / 0**。
崩溃链条正是从这里起步：门翻转 → 已雇实例变成"定义上不可用" → AI 评估解散 → 零成本除零。

## 3. A 类：222 个 AI 软门（核心病灶）

### 现状（以 `zys_jp_merc_2` 为例，`zys_east_mercenary.txt:20`）

```
zys_jp_merc_2 = { #僧兵
	regiments_per_development = 0.03
	cost_modifier = 1.5
	counts_towards_force_limit = no
	trigger = {
		is_allowed_to_recruit_mercenaries = yes
		if = {
			limit = { ai = yes }
			NOT = { army_size_percentage = 0.7 }   ← 兵力占比一变就翻转
		}
		if = {
			limit = { ai = yes }
			total_development = 150
		}
		culture_group = japanese_g
		religion_group = eastern
	}
}
```

### 为什么必须改

`army_size_percentage`（陆军规模 ÷ 兵力上限）是**每场战争、每次补员、每块地得失都会变**的量：

1. AI 国家开局兵力 < 70% → 30 个八旗/神族佣兵团全解锁，AI 大量雇佣（且 `counts_towards_force_limit = no` 不占编制，越雇越多）；
2. 兵力一旦 ≥ 70%，这些团**同时从可用池消失**；
3. 已雇的实例成了「定义上不可用但实体还在」的孤儿；
4. AI 逐 tick 清理 → 走解散路径 → `cost_modifier = 0.001` 使成本取整为 0 → **整数除零 C0000094**。

存档实证（`mp_autosave.eu4`，1481）：QNG 216 团、33 个 army 块，手上正握着
`zys_adg_merc_6`（cost 0.001）与 `zys_adg_merc_9`（cost 0.05）各一支实体单位，
而这两个团恰好都在这 222 个 AI 软门里 —— 门早就关了。

### 改法（三选一，请批准其中之一）

#### 方案 A1（推荐）：删软门 + dev 门降为裸条件

```
	trigger = {
		is_allowed_to_recruit_mercenaries = yes
		total_development = 150          ← 从 if 里提出来，变成对所有人的静态门槛
		culture_group = japanese_g
		religion_group = eastern
	}
```

- 删除全部 `if = { limit = { ai = yes } NOT = { army_size_percentage = 0.7 } }`（222 处）；
- 把 `if = { limit = { ai = yes } total_development = N }` 改成裸 `total_development = N`；
- 效果：AI 与玩家同规则；dev 门槛保留（原版 example 就是这么写的），且 dev 回落风险远低于兵力占比；
- 代价：**玩家也要满足 dev 门槛**（原本玩家完全豁免）。206 个团是 150 dev，早期大国无感，小国要等发育。

#### 方案 A2：只删兵力门，dev 门保持 AI 专属

- 删 222 处 `army_size_percentage` 块，保留 `if/limit/ai` 的 dev 门；
- 效果：玩家完全豁免，AI 受 dev 门；崩溃源去掉，但**玩家托管给 AI 时仍会遇到一次门翻转**（`ai = yes` 本身翻转）。
- 风险：比 A1 高一级，但改动最小。

#### 方案 A3：全删（两个 if 块一起删）

- 效果：所有团对所有国家按身份条件开放，无任何数值门；
- 风险：开局小国即可雇 30 个八旗团，平衡崩坏。

> 我的建议是 **A1**：它是唯一同时满足「零动态条件」「保留规模控制」「符合原版写法」三项的方案。

### A 类补充勘误（逐块剥离 if 后精确核验）

把 222 个块的 `if` 全部剥掉、只剩 `is_allowed_to_recruit_mercenaries` 的「空壳团」只有 **2 个**：

| 佣兵团 | 位置 | 情况 |
|---|---|---|
| `zys_tt_merc_37`（十大卡神） | `zys_east_mercenary.txt:3394` | 只有 `is_allowed` + 两个 AI 门，**无任何身份条件** |
| `zys_tt_merc_149`（雇佣骑手） | `zys_east_mercenary.txt:6364` | 同上；**存档里 QNG 正持有它**，属高危 |

这两个不能直接删门，必须补身份条件（例如 `home_province` 持有、`TAG`、`culture_group`），否则删完变成「全图任何国家顺手可雇」。

其余 **220 个**团的 trigger 里都还有真身份条件（`XXX = { country_or_non_sovereign_subject_holds = ROOT }` / `culture_group` / `religion_group` / `OR = { TAG = … }` / `has_idea` / `WAS_TAG`），删门安全。

另有 **11 个团只有兵力门、没有 dev 门**（删门后完全没有规模门槛，需单独决定是否补 `total_development`）：

`zys_jp_merc_6`(118)、`zys_jp_merc_8`(164)、`zys_tt_merc_15`(2791)、`zys_tt_merc_33`(3285)、
`zys_tt_merc_39`(3442)、`zys_tt_merc_43`(3549)、`zys_tt_merc_95`(4919)、`zys_tt_merc_99`(5011)、
`zys_tt_merc_106`(5196)、`zys_tt_merc_120`(5588)、`zys_tt_merc_121`(5615)

## 4. B 类：14 个 `ai = no` 裸条件

### 现状（`ACG_mercenary_extra_EXPAND.txt` 全文 14 个块，行 1/16/31/46/61/76/91/106/127/147/168/183/198/213）

```
ACG_MEC_EXPAND_new_mercenary_1 = {
	regiments_per_development = 0.1
	max_size = 160
	cavalry_weight = 0
	artillery_weight = 0.25
	sprites = { ... }
	trigger = {
		ai = no            ← 唯一条件
	}
	cost_modifier = 0.25
	manpower_pool = 75
}
```

### 问题

1. `ai = no` 意味着 **AI 永远看不到这 14 个团**；玩家托管 / 多人换手时状态翻转 → 同样会造成已雇实例非法化；
2. 除 `ai = no` 外**没有任何身份条件** → 全世界任何玩家国家都能雇；
3. `max_size` 160～400，是本 mod 里最大的团；
4. 全 mod 搜索 `ACG_MEC_EXPAND_new_mercenary_*`，除定义处外**零引用**（没有事件/决议/理念解锁它们），属于孤立内容。

### 改法（二选一）

- **B1（推荐）**：整段注释掉/删除这 14 个团。它们是模板内容、无引用、数值失衡（160~400 团无条件可得），删除不影响任何现有玩法。
- **B2**：保留但补身份条件，例如加 `is_allowed_to_recruit_mercenaries = yes` + `has_country_flag = <某个解锁 flag>`，并把 `ai = no` 去掉。需要额外做一个设 flag 的事件/决议，工作量更大。

## 5. 配套修正（崩溃的直接触发点，建议同批做）

### 5.1 `cost_modifier` 过低 —— 除零的分子

| 佣兵团 | 位置 | 现值 | 建议 |
|---|---|---|---|
| `zys_adg_merc_6`（随军驱口） | `zys_east_mercenary_amb.txt:154`（cost 在 158 行） | **0.001** | 0.25 |
| `zys_adg_merc_9`（满饷不可敌） | `zys_east_mercenary_amb.txt:225`（229 行） | **0.05** | 0.25 |
| `zys_jp_merc_6`（一领具足众） | `zys_east_mercenary.txt:118`（122 行） | **0.05** | 0.25 |
| `zys_tt_merc_64` | `zys_east_mercenary.txt:4076` | **0.05** | 0.25 |

参照：原版最低 `0.1`，旧 ACG1 最低 `0.01`（`kirara_mercenaries.txt:301/333`）。
`0.001` 是全套数据里唯一的异常值，且恰好挂在 QNG 手上（存档已证实）。

### 5.2 `min_size` / `max_size` 配对缺失 —— 规模失控

| 情况 | 数量 |
|---|---|
| 只有 `min_size`，无 `max_size` | **127** |
| 只有 `max_size`，无 `min_size` | 17 |
| 两个都没有（纯 `regiments_per_development`） | **101** |
| 成对齐全 | 9 |

`min_size` 无 `max_size` 时，团规模 = `regiments_per_development × 发展度`，无上限。
QNG 601 dev、`zys_adg_merc_6` 的 `rpd = 0.1` → 理论 60 团，维护费远超 AI 承受力 → 这正是 AI 决定「解散」的动机。

建议：给 127 个只有 `min_size` 的团补 `max_size = min_size × 3`（或按 `rpd × 400 dev` 估算），
给 101 个"双无"的团补 `min_size = 10`。此项属**平衡调整**，不是崩溃充分条件，可作为阶段 2。

## 7. 风险与不确定项

| 项 | 说明 | 处理 |
|---|---|---|
| AI 雇佣行为变化 | 去掉兵力门后 AI 会更积极地雇这些团，可能推高 AI 军费 | 观察一局；必要时用 `max_size` 而非 trigger 控制规模 |
| 玩家体验变化（A1） | 玩家也受 dev 门槛限制 | 若不想动玩家体验 → 选 A2 |
| `total_development` 仍是半动态 | 割地会掉 dev，理论上仍可能翻转 | 原版 example 就这么写，接受；若要求绝对静态 → 改用 `has_country_flag` |
| B1 删除 14 个团 | 无引用，但可能有玩家在用 | 先注释而不是物理删除，保留恢复可能 |
| `mercenary_desc_key = FREE_OF_ARMY_PROFESSIONALISM_AND_FORCELIMIT_COST` | 该 key 原版不存在（原版只有 `..._COST`） | 独立问题，不在本计划范围；若游戏内显示原始 key 再补本地化 |
